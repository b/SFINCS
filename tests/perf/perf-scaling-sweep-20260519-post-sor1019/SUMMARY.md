# SOR-1020 — scaling sweep re-run (post-SOR-1019)

Re-run of the [SOR-1017 scaling sweep](../perf-scaling-sweep-20260519/SUMMARY.md)
at a HEAD that includes both per-step halo-exchange coalescing fixes
([SOR-1018](../halo-exchange-profile-20260519/FINDINGS.md): q+uv;
[SOR-1019](../halo-exchange-cells-coalesce-20260519/SUMMARY.md):
zs+zsderv+z_volume cell halos). SOR-1017 verdicted all five
production cases as `per-step` on `gpu_n2 1x` — the unaccounted gap
`U(L) = total_simulation_time - sum(named components)` grew 70x-116x
from 1 h to 4 d while `per_step = U/step_count` stayed within
~15 % of its mean. SOR-1018 and SOR-1019 specifically target the
per-step CUDA-MPI halo exchange that profiling identified as the
dominant contributor. This sweep captures the same 5×4×3×(1-2)
matrix at the post-fix HEAD so the cumulative delta can be
quantified per case and the verdict re-evaluated.

The "delta vs SOR-1017 baseline" section below is mechanically
generated from `../perf-scaling-sweep-20260519/<case>__1x__4d__gpu_n2/timings.txt`
(pre-fix, HEAD `2137fc0`) against this directory's same cell
(post-fix, HEAD recorded in `capture_env.txt`).

## Decision rule (verdict per case)

For each `(case, grid, config)` tuple with all four lengths present,
compute at each length L:

```
U(L)         = simulation - (boundaries + momentum + continuity + snapwave + meteo + output)
step_count   = (tstop - tstart) / avg_dt + 1
per_step(L)  = U(L) / step_count(L)
```

Then:

* **`fixed-cost`** when `U(L)` is roughly constant
  (`max(U) - min(U) < 0.5 * mean(U)`) AND `per_step(1h) / per_step(4d) >= 5x`
  (i.e. the gap is amortized away as the step count grows).
* **`per-step`** when `per_step(L)` is roughly constant
  (`max(ps) - min(ps) < 0.5 * mean(ps)`) AND `U(4d) / U(1h) >= 3x`
  (i.e. the gap grows in step with the step count).
* **`inconclusive`** otherwise — run-to-run noise or a mix of the
  two regimes prevents a clean call.

The verdict is reported per case for the `gpu_n2` `1x` configuration
(the one the issue body identifies as carrying the unaccounted-time
question). The `cpu_n128`, `gpu_n1`, and `4x`-grid rows are tabulated
for context but are not verdict-bearing.

## Methodology

Captured by `run_perf_scaling.sh` in this directory; orchestration
log in `run.stdout`; host fingerprint in `capture_env.txt`. Each
cell below is one run per `(case, grid, length, config)` — no
per-cell averaging. The CPU caveats from SOR-87 apply (single-shot
`cpu_n128` wall has wide variance on this 128-thread host).

* **Configurations:**
  * `cpu_n128` — gfortran/OpenMP, `OMP_NUM_THREADS=128`,
    `OMP_PROC_BIND=true`, single process.
  * `gpu_n1` — CUDA build, `mpirun -n 1` inside `sfincs-build-gpu:latest`.
  * `gpu_n2` — CUDA build, `mpirun -n 2` inside `sfincs-build-gpu:latest`.
* **Simulation lengths:** 1 h, 6 h, 24 h, 4 d — `tstart` fixed at
  `20200101 000000`; `tstop` is rewritten in the staged `sfincs.inp`.
  SFINCS's adaptive timestepper (bounded by `dtmax=60.0` for these
  cases) decides the resulting step count at run time.
* **Grids:**
  * `1x` — native grid as shipped under `tests/cases/<case>/`.
  * `4x` — only for `case_prod_regular_tide`: `mmax`, `nmax` doubled
    (cell count 4x), `dx`, `dy` halved, bathymetry / mask / tide
    forcing regenerated by `generate_4x_regular_tide.py` (the case's
    own `generate.py` re-run with the refined dimensions). The four
    other cases ship with auxiliary forcing files (quadtree netcdf,
    subgrid lookup, on-grid SCS / meteo) whose refinement is out of
    scope for a perf-only harness; per-case skip rationale:
    * `case_prod_quadtree_subgrid_tide` — refining the computational
      mesh requires regenerating the precomputed quadtree netcdf
      (`sfincs.nc`) and its subgrid lookup (`sfincs_subgrid.nc`),
      which would require a full HydroMT-SFINCS preprocessing run.
    * `case_prod_riverine` — `sfincs.scs` is an on-comp-grid ASCII
      array; refining the grid requires re-running the SCS-CN
      preprocessing pipeline.
    * `case_prod_storm_amuv` — `sfincs.scs` / `sfincs.ks` /
      `sfincs.sigma` / `sfincs.psi` are on-comp-grid ASCII arrays
      with the same regen blocker.
    * `case_prod_compound_snapwave` — quadtree + subgrid + SnapWave
      grid coupling. Same regen blocker as `quadtree_subgrid_tide`.

## Synthesis

**All five cases retain the `per-step` verdict on `gpu_n2 1x`.** The
SOR-1018 + SOR-1019 coalescing reduced `U(L) = simulation -
sum(named components)` by 8 %–36 % at the `4d` length without
collapsing the per-step trend: `U(4d) / U(1h)` is 72x-129x post-fix
(vs 70x-116x pre-fix), and `per_step` remains within ~15 % of its
mean across the four lengths in every case. The unaccounted gap
still scales with step count — the halo-exchange contribution to
that gap shrank, but a residual per-step cost remains in every
case.

**Coalescing leverage tracks halo-exchange share of U(L) per case.**
The two tide cases — whose pre-fix U(L) was dominated by the
per-step halo exchange — saw the largest absolute per-step
reduction: `quadtree_subgrid_tide` `−29.6 %` and `regular_tide`
`−23.9 %`. `compound_snapwave` saw the largest *percentage*
reduction in U(L) (`−36.1 %`) but its U(L) was only ~8 % of total
simulation time pre-fix (SnapWave still accounts for ~84 % of the
4 d wall), so the absolute wall delta is `−9.5 s` of 232 s
(`−4.1 %`). The meteo-coupled cases (`riverine` `−10.1 %`,
`storm_amuv` `−8.4 %` on U(L)) sit in between — halo exchange was
a smaller share of their pre-fix U(L), so the coalescing leverage
was correspondingly smaller.

**New largest contributor to U(L) per case (4 d, 1x, gpu_n2).**

| case | post-fix per_step | what's left in U(L) |
|------|-------------------|---------------------|
| `case_prod_regular_tide`           | 0.081 ms/step | 11.6 s residual on a 35 s wall; momentum (13.6 s, 39 %) is now the largest named component. U(L) is the second-largest slot (33 %). |
| `case_prod_quadtree_subgrid_tide`  | 0.096 ms/step | 10.6 s residual on a 33 s wall; continuity (9.8 s, 30 %) is the largest named component. U(L) close behind at 32 %. |
| `case_prod_riverine`               | 0.757 ms/step | 72.3 s residual on a 103 s wall — U(L) is **70 % of simulation**. Meteo (18.6 s, 18 %) is the largest named component but U(L) dominates by ~4x. |
| `case_prod_storm_amuv`             | 0.717 ms/step | 86.4 s residual on a 176 s wall — U(L) is **49 % of simulation**. Meteo (67.8 s, 39 %) is the largest named component; U(L) is the second-largest slot. |
| `case_prod_compound_snapwave`      | 0.113 ms/step | 12.4 s residual on a 221 s wall. SnapWave (185.7 s, 84 %) dominates the cell; U(L) is only 5.6 % of simulation. |

**Throughput-ceiling re-check.** At the `4d` cell, `gpu_n2 max sm %`
medians: `regular_tide 1x` 47 %, `regular_tide 4x` 70 %,
`quadtree_subgrid_tide 1x` 39 %, `riverine 1x` 24 %, `storm_amuv 1x`
22 %, `compound_snapwave 1x` 0 %. `regular_tide 4x` `gpu_n1` still
saturates at 89 % (matching the SOR-1017 reading) — the only
case-config combination above the 80 % bar on this hardware. The
qualitative picture from SOR-1017 ("only the 4x regular_tide cell
is GPU-bound; the rest are too small per rank or host-bound") is
unchanged.

**Crossover (gpu_n2 vs gpu_n1).** The `4x` `regular_tide` case
shows the same within-case crossover as in SOR-1017: `gpu_n1` wins
at 1 h (`0.91x`), `gpu_n2` wins from 6 h onward (`1.18x-1.30x`).
The `riverine` and `storm_amuv` cases now show `gpu_n2` winning at
every length (ratios `1.20x-1.51x`), slightly stronger than the
pre-fix readings — consistent with the halo-exchange path being a
larger relative cost on `gpu_n2` than `gpu_n1`, and so reaping more
of the coalescing savings.

* **`riverine` / `storm_amuv` per-step `0.72-0.76 ms/step`.** U(L) is

  named-component portion of meteo work, so this residual is
  something else — candidate explanations: per-step host-side
  coordination around the meteo dispatch, unbatched kernel launches
  in the meteo→momentum hand-off, or remaining device→host
  synchronization not yet on the coalescing path. The halo-exchange
  share of U(L) on these cases pre-fix was small (8-10 %
  improvement post-coalesce); the bulk of U(L) is elsewhere.
* **`regular_tide` / `quadtree_subgrid_tide` per-step `0.08-0.10 ms/step`.**
  Order-of-magnitude smaller than the meteo-coupled cases but still
  above the 0.05 ms threshold the task body flagged. The
  coalescing already cut these by `−24 %` / `−30 %`; a further
  pass on the same code path (e.g. coalescing more variables, or
  fusing pre/post halo kernels) is unlikely to close the rest by
  itself given the diminishing-returns shape of the deltas.
* **`compound_snapwave` SnapWave kernel — 84 % of the cell.** Not a
  U(L) problem; SnapWave is a named component running host-side
  (note `gpu_n2 max sm % = 0 %` at 6 h / 24 h / 4 d). A SnapWave
  GPU port (deferred per SOR-81 per the SOR-1017 SUMMARY) is the
  only lever that moves this cell.
