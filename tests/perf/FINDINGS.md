## Numerical correctness preservation

The pre-fix and post-fix `sfincs_map.nc` files compare bit-exact under
`tests/scripts/diff_zsmax.py`:

```
RESULT case=pre-fix ref=tests/perf/post-fix/sfincs_map.nc cand=tests/perf/pre-fix/sfincs_map.nc max_abs_diff=0.0 max_zsmax_ref=0.9975454807281494 ratio=0.0 threshold=1e-06 verdict=PASS
```

This is expected: the bytes on the MPI wire are `real*8 → MPI_DOUBLE_PRECISION
→ real*8` whether routed via GPUDirect / cuda_copy or via host staging.

For the full per-case bit-equivalence sweep, see
`tests/perf/case_sweep_prefix.log` (generated by

## Why pre-fix vs post-fix numbers match in this container

The issue body assumed two distinct OpenMPI installations under NVHPC 25.9:
a CUDA-aware HPC-X 2.24 under `comm_libs/13.0/hpcx/hpcx-2.24/`, and a
separately-built non-CUDA-aware OpenMPI under `comm_libs/mpi/`. In the
actual `sfincs-build-gpu:latest` image both `mpirun` paths resolve to
the same HPC-X 2.24 process:

1. `comm_libs/mpi` is a **symlink** to `comm_libs/hpcx`. The "default"
   `mpirun` at `comm_libs/mpi/bin/mpirun` is a 319 KB wrapper that
   internally execs the full HPC-X mpirun at
   `comm_libs/13.0/hpcx/hpcx-2.24/ompi/bin/.bin/mpirun`. Verified via
   `ps --forest` during the pre-fix run, which shows the
   `comm_libs/mpi/bin/mpirun` → `comm_libs/13.0/hpcx/latest/ompi/bin/mpirun`
   → `comm_libs/13.0/hpcx/hpcx-2.24/ompi/bin/.bin/mpirun` chain.
2. The SFINCS GPU binary is dynamically linked with `DT_RUNPATH` pointing
   at `comm_libs/13.0/hpcx/hpcx-2.24/ompi/lib`. There is no second
   `libmpi.so.40` anywhere in the image (`find / -name 'libmpi.so*'`
   returns only the HPC-X copy), so the dynamic loader resolves
   `libmpi.so.40` to HPC-X regardless of `LD_LIBRARY_PATH`.
3. The pre-fix variant additionally passes
   `--mca opal_cuda_support 0 --mca mpi_cuda_support 0` to disable the
   CUDA-aware runtime path at the OMPI layer (closest in-container
   proxy for "non-CUDA-aware MPI"). `MPIX_Query_cuda_support` still
   reports `1` because it reflects build-time support, not the runtime
   toggle, and UCX continues to handle GPU pointers via its own
   `cuda_copy` / `cuda_ipc` / `gdr_copy` transports regardless of the
   OPAL flag; the rank-0 `CUDA-aware MPI: yes (MPIX_Query_cuda_support=1)`
   log line appears in both variants.

Net result: this container has effectively one MPI stack, and the
SFINCS binary's link recipe makes the choice non-runtime-overridable.
The PATH / LD_LIBRARY_PATH / OPAL_PREFIX layering in
`source/build_scripts/run_gpu_container.sh` + `Dockerfile_gpu` and the
`MPIX_Query` rank-0 verdict in `sfincs_partition.cuf` are still
load-bearing **as defense-in-depth**:

* When (not if) NVHPC's container layout changes — e.g. NVHPC 26.x
  re-introduces a separate non-CUDA-aware MPI under `comm_libs/mpi`,
  or a downstream image rebuilds SFINCS against system OpenMPI — the
  wrapper / Dockerfile fix prevents silent regression.
* When an operator builds SFINCS outside this container (custom
  cluster module, manual cmake / autotools, a different MPI
  implementation) the `MPIX_Query` rank-0 line gives a one-line
  status; a multi-rank GPU run that prints
  `WARNING: MPI is not CUDA-aware` is immediately diagnosable as the
  failure mode described in the issue body.

## The `force-non-cuda-aware` empirical finding

The issue body hypothesized that a non-CUDA-aware MPI silently stages
every device-pointer Isend through pinned host memory via UVA page
faults, saturating one CPU thread and stalling the GPU. The actual
behaviour of HPC-X 2.24's OpenMPI when its CUDA-aware transports are
forcibly disabled is **immediate SIGSEGV** at the first halo exchange,
not slow-but-working host staging.

Reproducing the failure mode:

```sh
tests/perf/run_perf.sh force-non-cuda-aware
```

`force-non-cuda-aware` runs SFINCS against HPC-X mpirun with the
following environment imposed:

```
UCX_TLS=tcp,sm,self          # drops cuda_copy / cuda_ipc / gdr_copy
UCX_MEMTYPE_CACHE=n          # disables the addr → memtype cache
--mca opal_cuda_support 0    # disables OPAL-layer CUDA detection
```

With UCX restricted to CPU-only transports and OPAL CUDA off, MPI has
no CUDA-aware path available. SFINCS's first
`MPI_Isend(halo_send_buf_q_uv_r8, ...)` from
`halo_exchange_q_uv` (`source/src/sfincs_partition.cuf:2882`) reaches
`ucp_tag_send_nbx → uct_mm_ep_am_short`, which dereferences the
device pointer as a host buffer; the kernel reports
`Caught signal 11 (Segmentation fault: invalid permissions for mapped
object)` and both ranks abort. The committed
`tests/perf/force-non-cuda-aware/sfincs.stdout` carries the full UCX
+ OMPI stack trace pinning the failure at:

```
 6 PMPI_Isend()
 8 sfincs_partition_halo_exchange_q_uv_()  /work/source/src/sfincs_partition.cuf:2882
```

Implications:

1. **There is no "slow but working" non-CUDA-aware data path for the
   SFINCS GPU binary on this container.** Either CUDA-aware MPI is
   available (binary runs) or it isn't (binary crashes). The AC's
   `Expected` sub-bullets describe a wall-clock spectrum
   (100 % CPU + 35 % GPU + huge transfer rates → near-idle CPU +
   75 – 90 % GPU + near-zero transfers) that does not exist for this
   binary in this stack — the data path is binary, not analog.
2. **The fix matters more than the issue framing suggested.** The
   defense-in-depth wrapper / Dockerfile / harness / rank-0 logging
   is the safety net for an operator who ends up on a stack where MPI
   isn't CUDA-aware: their run won't be slow, it will SIGSEGV at the
   first halo exchange with an opaque "invalid permissions" address.
   The pre-flight `assert_cuda_aware_mpi` in `tests/run_validation.sh`
   /  `tests/run_benchmarks.sh` and the `MPIX_Query` verdict at SFINCS
   startup catch the misconfiguration before it produces that
   stack trace.

## Why the GPU utilization sits at ~17 – 19 % and rank-0 CPU% at ~100 %

The AC's expected post-fix profile is "rank-0 CPU near-idle, GPU
75 – 90 %, PCIe near-zero except at SnapWave / output cadence". The
measured profile under CUDA-aware HPC-X (`post-fix`) is:

* rank-0 %CPU steady-state: 97 – 101 % (mostly 100 %)
* GPU sm %: alternates between 0 (SnapWave / I/O windows) and 18 – 19 %
  (SFINCS compute kernels)
* PCIe Tx: sustained 2 200 – 2 500 MB/s
* PCIe Rx: sustained 1 000 – 1 100 MB/s

The dominant cost is SnapWave (43 % of total runtime per `sfincs.log`):
`Time in SnapWave : 13.95 s` vs `momentum 5.50 s + continuity 4.76 s`
combined. SnapWave runs CPU-side and bridges arrays in/out of device
memory at every SnapWave update cadence (`dtwave = 1800 s`), which is
where the sustained PCIe traffic comes from. OMPI's default progress
engine also busy-polls on the MPI progress thread; rank-0 stays at
~100 % CPU even when no SFINCS work is in flight, because the busy
poll counts toward `%CPU`.

That is on the out-of-scope list for SOR-52 ("The SnapWave bridge
H↔D copies that happen at the SnapWave update cadence are correct
and intentional; SnapWave runs CPU-side"), so this fix neither
targets nor changes it.

## Concurrent-run caveat (capture-time orphan)

During the captures the host had an orphaned `sfincs` container from a
prior session still attached to both GPUs (visible via `docker ps` as
`sfincs-build-gpu-3691036-1778902600`, alive for hours):

```
3691466  ...  sfincs (rank 0, idle)         GPU 0, ~300 MiB
3691467  99%CPU 5h+    sfincs (rank 1, hot) GPU 1, ~300 MiB
```

That orphan is a textbook instance of the symptom described in the
issue body — one rank pegged at 100 % single-thread CPU, the other
idle — running for hours on a stale validation invocation. It was
left untouched (cross-session cleanup is out of scope here) but its
ambient ~600 MiB of GPU memory and intermittent SM contention may
slightly bias the dmon numbers upward (more PCIe noise) and the wall
clock downward (the orphan was MPI-idle, not GPU-busy, during the
capture window). Repeating the capture with a clean host would not
be expected to change the qualitative finding that both variants
behave identically.
